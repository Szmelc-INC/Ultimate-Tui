In short: match model+effort to task difficulty (cheap model for mechanical work, strong model + high effort only for real thinking); grep/glob before Read and read only the needed range; never re-read a file just to verify an edit; batch independent tool calls; stop when you have the answer; verify programmatically (targeted tests/compile), not by eye; keep the context prefix stable. ## Project status

MVP built. Go module `github.com/silverx/ultimate-tui` (Go 1.26). A config renders end to end: recursive row/column splits; `text`, `markdown`, `command`, interactive `shell` (pty), `input` (bubbles/textinput), `list` (bubbles/list) and `form` (huh) widgets; focus ring; a **NAV/LOCKED** focus model (arrows = directional focus, Enter locks a pane, Esc releases, `Esc Esc` = literal Esc to a child); `mod+`-prefixed keybindings (`mod` = Alt by default); **Ctrl+C = confirm-quit in NAV / kill-this-pane's-process when LOCKED** (no bare quit).

**Pane geometry vs. content are two separate axes**, on purpose (this used to be one conflated "zoom" feature — don't re-merge them): `mod+arrows` **resizes** the focused pane directionally, growing it toward the arrow's edge at the expense of whichever sibling sits there (written as real percents onto `Child.Size` — no rebuild, `render` re-reads `Size` every frame); `mod+shift+arrows` **swaps** the focused pane with that same neighbor (exchanges `config.Node` content, `Size` stays with the slot — this *does* need `rebuild()`, since pane identity moves between `Child` slots); `mod+s` **flips** the focused pane's enclosing split between row/column. `mod+=` / `mod+-` / `mod+0` is a separate per-pane **content zoom** — scales what a widget *draws* (via the optional `widget.Zoomer` interface; the `text` widget implements it with a compact 3x5 block-glyph font, `bigfont.go`) without touching the pane's rectangle at all.

**Mouse drag mirrors the keyboard, and then goes further**: `mod+left-drag` grabs a pane and swaps it with whatever it's dropped on; `mod+right-drag` grabs it to resize, converting cursor movement into `resizeFocusedBy` calls — unlike `mod+arrows` (always grows), a drag from an arbitrary grab point falls back to *shrinking* the pane's opposite edge when there's no neighbor to grow into on the dragged side, so grabbing anywhere and dragging any direction always resizes something the layout has room to give (see `dragResizeAxis`, `resize.go`'s `resizeFocusedBy`). Cursor movement is throttled two ways so a drag stays controllable rather than twitchy: `dragCellsPerStep` cells cost one resize step, and `dragMaxStepsPerEvent` caps how many steps one motion event applies (a fast drag arrives as a few events with large deltas, not many with `dx=1`, so the per-cell divisor alone can't bound a single event) — leftover movement isn't discarded, `dragLastX/Y` only advances by what was actually applied, so a follow-up event keeps consuming it. Holding `mod` preempts the plain right-click context menu entirely.

The pane tree is **structurally editable at runtime**, not just its leaves' fields: a pane context menu (right-click, or `mod+w`) offers **Stop / Restart / Refresh / Split / Close / Edit** (process actions grey out for widgets that don't support them; Close greys out on the last pane); right-clicking dead space — the status bar row, the only spot the tree doesn't tile — opens a one-item **New pane** menu that wraps the whole layout via the same split-prompt overlay Split uses (direction + a keep-percent slider). Any edit that changes the `Children` slice's shape (Split, Close, New, swap) goes through `Model.rebuild()`, which re-derives the whole leaf tree from `cfg.Layout`, carries every widget over by `*config.Pane` **pointer identity** (a split does not respawn the pane it split; a resize never touches a widget at all), `Close()`s any widget whose pane is no longer reachable, and lets the caller re-resolve a captured `*config.Pane` back into an index via `indexOfPane` — every index the engine holds (`m.focus`, `m.ctxLeaf`, leaf `.parent`/`.split`/`.chain`) is invalidated by a Go slice reallocation, so nothing may reshape `cfg.Layout` without calling `rebuild()` immediately after.

An F1 help popup; an **F2 control panel** (this TUI's own settings: a **Theme & style** row opens the live picker, an **Edit config** row opens the whole-config editor); an **F3 global settings panel** — runner-wide `mod`/status-bar toggle plus a read-only "this run" block (config path, global config path, resolved binary, config-file permissions, pane count, mode) — deliberately **not** in `isGlobalKey` (handled directly in the NAV-only key switch instead), so it only opens from NAV and a locked shell/vim keeps its own F3; a bottom status bar.

A **pane editor** overlay reached from the context menu's Edit row — a roomy tab navbar (General / Layout / Widget) over typed controls (select for `type`/`direction`/`markdownStyle`, free-text for `title`/`content`/`command`/…, on-off for `border`, mode+slider for `size`), wider fields and a blank spacer row between them, a minimum panel width (`padBlockWidth`) so a short tab doesn't look squeezed. Edits are buffered and applied on `mod+s`/`Enter` (mutates the live `*config.Pane`/`*config.Child`/enclosing `*config.Node` in place — each `leaf` keeps `pane`/`parent`/`split` pointers to them — and rebuilds the widget when a widget-affecting field changed, closing the old one first). `render` re-reads `Direction` from `node.cfg` and `Size` from `child.cfg` every frame so a `direction`/`size` edit shows immediately. The same overlay opens **whole-config** from F2's "Edit config" row — a leading "Config" tab adds the top-level `name` and a pane selector that walks every leaf (committing the pane it leaves), and a **Keybinds** tab lists/edits/removes (`ctrl+d`)/adds (`+ add keybind` row) `cfg.Keybindings` entries, sorted by key — applying calls `Model.rebuildKeyMap()` (factored out of `NewWithOptions`) so an edited or new binding works immediately, no restart. `Enter` applies to the running UI, `mod+s` also writes the file (`Options.SaveConfig` → `config.Save`), and `Esc` with unsaved edits raises a discard confirm (`cfDiscard`).

**Every overlay is mouse-drivable**, not just the pane tree: each overlay's panel stamps its own bounding box every render (`splice()`, `chrome.go`); a click **outside** that box dismisses the overlay exactly like Esc (routed through the same per-overlay Esc handling — cancel, discard-confirm, return-to-parent, whatever that overlay's Esc already does), a click **inside** hits that overlay's own row/field/tab, and wheel adjusts a slider/list where that makes sense. Mouse elsewhere: click-to-focus, wheel-scroll, right-click opens the context menu.

A **global runner config** at `~/.config/ultui/config.json` (`ultui config` to inspect, F3 to edit mod/statusbar live); three run modes (runtime / headless / go:embed-static). `DESIGN.md` is the vision; `README.md` and `LLM.md` document what actually exists.

## Architecture decisions (do not undo)

- **Widgets are a compile-time registry, not plugins.** `widget.Register(kind, factory)` + config selecting a kind by name. No `plugin.Open`, no `dlopen`, no subprocess-as-module. This is what makes "runtime, dynamic-linked, and static-linked" the *same engine* — runtime reads config from disk, static `go:embed`s it, dynamic reads a path; all call `engine.Run`. "Total modularity" from `DESIGN.md` will tempt a rewrite toward plugins — resist; add a widget file instead.
- **Config is strict JSON.** `DESIGN.md`'s "markdown json" was ambiguous; resolved to one strict decoder (`DisallowUnknownFields`, so typos error). Nodes are split-XOR-leaf by key presence, not a discriminator field.
- **Two process widgets, on purpose.** `command` runs once and captures text into a scroll pane. `shell` hosts a *real interactive process* (htop, vim, cmatrix, `$SHELL`) on a pty, feeds its output through a `charmbracelet/x/vt` emulator, and forwards keystrokes via `keyToBytes`. Don't merge them; don't make `command` grow a pty.
- **Focus lock replaces the tmux prefix.** Two modes. **NAV**: arrows do directional focus, `Tab` cycles, `Enter` locks the focused pane, bound keys run their action, unbound keys fall through to the widget. **LOCKED**: every key goes to the focused widget — this is when a `RawKeyConsumer` (`shell`) pane actually receives raw keys, so htop/vim get their own `q`/F-keys. `Esc` releases; on a raw pane the first `Esc` buffers and `Esc Esc` sends a literal `Esc` to the child. `isGlobalKey` — anything starting `mod+` (mod = Alt by default, set in the global config), plus `F1` (help) and `F2` (control panel) — is intercepted in **both** modes; this is also how the resize/swap/flip-split/content-zoom bindings (`mod+arrows`, `mod+shift+arrows`, `mod+s`, `mod+=/-/0`) work identically NAV or LOCKED. `F3` is deliberately NOT in `isGlobalKey`: it's a hardcoded case in the NAV-only key switch (same place `Enter`-to-lock lives), so it only opens from NAV and falls through to the focused widget when locked — a locked shell/editor keeps its own F3. `Config.Prefix` is parsed-but-ignored (kept so old configs don't fail `DisallowUnknownFields`). Don't reintroduce a leader-key state machine.
- **Pane geometry and pane content-scale are separate features — never conflate them again.** `mod+arrows`/`mod+shift+arrows` (resize/swap, `resize.go`) mutate `Child.Size` / swap `config.Node` content — real config state, no widget involved. `mod+=/-/0` (content zoom) only ever calls `widget.Zoomer.SetZoom` on the focused leaf's widget — it never touches layout. This split replaced a single "zoom" feature that conflated the two (see git history if you need the old `shiftZoom`/`zoomCells` sum-preserving-bias math — deleted, not worth resurrecting). Resize writes real percents (`resizePercents` snapshots the split's currently-computed sizes to whole percents first, so a fixed/flex split gets pinned to percent on its first `mod+arrow` rather than drifting) and needs no `rebuild()` — only `Size` strings change, `render()` re-reads them every frame. Swap **does** need `rebuild()` — it moves which `*config.Pane` lives in which `Child` slot, so every leaf's `.parent`/`.split`/`.chain` downstream of the swap is stale until re-derived. `mod+drag` (`drag.go`) is the mouse version of both: `mod+right-drag` converts cursor delta into `resizeFocusedBy` calls live during the drag (via `dragResizeAxis`, which tries growing toward the drag direction first and falls back to shrinking the opposite edge when that side has no neighbor — a plain `resizeFocused`/`mod+arrow` never shrinks); `mod+left-drag` grabs a pane and swaps it with whatever it's dropped on. Holding `mod` preempts the plain right-click context menu — check that branch first in `handleMouse` if you touch it.
- **Structural pane-tree edits (Split/Close/New/swap) always end in `rebuild()`.** `Node.Children` is `[]Child` *by value* — appending or removing reallocates it, silently stranding every `*config.Child`/`*config.Node` pointer the engine already holds (`leaf.parent`, `leaf.split`, every `ancestorLink` in `leaf.chain`) and invalidating every index (`m.focus`, `m.ctxLeaf`, `m.confirmLeaf`). `rebuild()` (`rebuild.go`) re-walks `cfg.Layout` via `build()`, carrying each live widget over by `*config.Pane` **pointer identity** (a `map[*config.Pane]*leaf` snapshot taken before the edit) so a Split never respawns the pane it split and a Close only tears down the pane actually removed; anything in the old snapshot not reachable from the new tree gets `Closer.Close()`d. Callers capture a `*config.Pane` *before* mutating the tree and re-resolve it via `indexOfPane` *after* — never hold a leaf index across a structural edit. `Close` (`closeLeaf`, `split.go`) refuses the last pane, collapses a two-child split into its surviving sibling (never leaves a degenerate one-child split node), and renormalizes percent siblings otherwise. New panes default to `type: "text"` (a pane needs a non-empty `Type` or `config.Save` fails `Validate()`).
- **Ctrl+C is never a bare quit.** It is handled directly in `handleKey`, not the bindings map, and is deliberately *not* in `isGlobalKey`. NAV: raises the `ovConfirm` quit dialog (`y`/`Enter`/second `Ctrl+C` = quit, `n`/`Esc` = cancel). LOCKED: `lockedInterrupt` — a pane implementing `widget.Interrupter` gets a "kill this pane's process?" confirm and, on yes, only that child dies (`shell` drops to its exit overlay, program keeps running); a plain pane just receives the key. `mod+q` was removed — the way out of a locked pane is `Esc` then `Ctrl+C`. Don't re-add an unconditional quit key.
- **Overlays are one enum, one splice.** `m.overlay` ∈ `ovNone/ovHelp/ovConfirm/ovSettings/ovControl/ovContext/ovEditor/ovSplit/ovGlobal`; at most one is active. `ovConfirm` is shared: `confirmKind` ∈ `cfQuit/cfKill/cfDiscard/cfClose` picks the payload, and `cfDiscard`'s "no" returns to `ovEditor` (not `ovNone`). `m.overlayReturn` is a **one-level** back target: the F2 control panel (or F3) sets it to `ovControl` (or `ovGlobal`) before opening the picker, so Esc/Enter from the picker land back where it opened from, and a second Esc closes. `handleKey` routes every key to the active overlay first. `View` splices exactly one panel via `m.splice(frame, panel)` (`chrome.go`) — a thin wrapper over `overlayCenter` (ANSI-safe, `x/ansi` `Truncate`/`TruncateLeft` — does not blank the background) that also stamps the panel's bounding box (`m.ovX/Y/W/H`) every render. Add a new modal as an enum member, not a parallel bool.
- **Every overlay is mouse-drivable, click-outside dismisses.** `Update` no longer drops `tea.MouseMsg` while `overlayActive()` — it routes to `handleOverlayMouse` (`overlay_mouse.go`). A left/right press outside the stamped bounding box is treated exactly like Esc, routed through `handleKey` so each overlay's own Esc semantics apply unchanged (cancel a confirm, discard-confirm from the editor, return-to-parent from a nested picker — never a generic "close"). A press inside is converted to content-relative coordinates (every panel shares the same `th.helpBox` border+padding, so the offset — `panelContentOffsetX/Y` — is one constant for all of them) and handed to that overlay's own hit-test (`contextMouseClick`, `controlMouseClick`, `settingsMouseClick`, `splitMouseClick`, `editorMouseClick`, `globalMouseClick`, `confirmMouseClick` — each one row/field/tab per content line, kept in sync with the matching render function by sharing named row constants, e.g. `edFieldsStart`/`edFieldStride`/`edTabRow` for the editor, not by two hand-matched magic numbers). The context menu's rows *run on click* (button semantics); editor/split fields *select* on click (form semantics) — Enter/arrows still do the rest. The `cfKill`/`cfClose` dialogs and the context menu / editor both capture their target leaf index (`confirmLeaf` / `ctxLeaf`) at open time, not by re-reading `m.focus`, so an outside click that dismisses the modal behind it can never redirect the action to a different pane.
- **Theming = palette × styleset, resolved once.** `theme.go` has a `palettes` registry (`auto` adaptive; `tokyo-night`/`gruvbox`/`slate`/`midnight` concrete `lipgloss.Color` — named themes must NOT be adaptive) and a `stylesets` registry (`rounded`/`double`/`heavy`/`ascii` = border + status-bar/lock glyphs; `ascii` is pure 7-bit for non-Nerd-Font terminals). `(*Model).theme()` builds + memoizes; `invalidateTheme()` drops the memo (picker live preview). Unknown names fall back to the default in the engine but `main.go` rejects them up front (strict-config parity). The F1/confirm/settings panels, status bar and pane borders all read from the resolved `theme` — no hardcoded colours or box chars outside `theme.go` (the one known exception: `shell.go`'s exit bar, which is in the `widget` package and can't import `engine`).
- **Theme/style picker persists via a callback.** `Options.SaveTheme func(theme, style string) error` is nil in `DefaultOptions`/tests (engine never writes disk); `main.go` wires it to `config.SaveGlobalThemeStyle`, which load-mutates-renames the global config touching only `theme`+`style`. The picker (reached from the F2 control panel, or F3) previews live on cursor move, commits only on `Enter`, restores `setSavedTheme/setSavedStyle` on `Esc`; either way it returns via `overlayReturn` to whichever of F2/F3 opened it.
- **Engine stays config-file-agnostic.** `engine.New/Run/Snapshot` use `DefaultOptions()`; `*WithOptions` variants take an `engine.Options`. The global runner config (`config.LoadGlobal`) is read **only in `main.go`** and folded in via `OptionsFromGlobal` — so tests never depend on `~/.config`. Same rule for every other disk touch: `Options.SaveConfig func(*config.Config) error` is nil in `DefaultOptions`/tests; `main.go`'s `cmdRun` wires it to `config.Save(cfgPath, c)` (marshal-indent + tmp + rename, `Validate()` first — mirrors `SaveGlobalThemeStyle`). `Options.SaveGlobal func(*config.GlobalConfig) error` (nil likewise) is F3's save target, wired to the new `config.SaveGlobal` (replaces the whole file, unlike `SaveGlobalThemeStyle`'s load-mutate-preserve) — `applyGlobal` (`global.go`) always carries `m.opts.Keys` (this run's already-resolved global keybindings) into the `GlobalConfig` it saves, so saving mod/statusbar can never silently drop a hand-edited global keybinding it never touched. `Options.ConfigPath`/`GlobalConfigPath` are plain informational strings `main.go` resolves and hands over for F3's "this run" block — the engine still never touches either path itself. The editor mutates the in-memory `*config.Config`/`*config.GlobalConfig` regardless; only persistence needs a callback.
- **Status bar owns the last row.** When shown (`Options.StatusBar` && height ≥ 6) the layout tree gets `height-1`; `rectW/rectH` are stamped to that body size and mouse/`focusDir` staleness checks compare against `bodyDims()`, not the raw terminal size.
- **Mouse.** `render` records each leaf's absolute rect (stamped with the size it was computed at); `handleMouse` hit-tests `tea.MouseMsg` against them — left-press focuses, wheel scrolls the pane *under the cursor* without moving focus, right-press opens the context menu (`openContext(-1)` for the status-bar row — the one spot the tree doesn't tile — opens the "New pane" menu instead). Mouse events are ignored when the rect stamp ≠ current size (stale) or before the first `View`. `mod`+drag (`drag.go`) preempts all of the above, including the plain right-click menu — check `m.dragMode != dragNone || msg.Alt` first if you touch `handleMouse`. Overlay mouse routing is separate: see `handleOverlayMouse` two bullets up.
- **`Snapshot` is bounded.** A `shell` read loop is infinite by design, so `drain` runs each command with a timeout + step/elapsed caps and applies a `StreamMsg` once without following it. `Snapshot` always `m.Close()`s to kill spawned children. Interactive apps that paint on a timer (htop) won't have painted in a headless frame — that's expected; `run` gives them real time.
- **lipgloss sizing in `renderLeaf`:** `Width/Height` set the content area, a border adds 2 outside. Never put `MaxWidth/MaxHeight` on a bordered style — it clips the final output including the border and shears an edge.
- **Status bar exact width is `lipgloss.Width`-measured.** `statusBar` computes `gap = w - Width(left) - Width(hint)`; the mode-chip glyph comes from the styleset, and Nerd Font glyph cell-widths are exactly where lipgloss and the terminal can disagree — any new styleset glyph needs the `TestStatusBarWidthHoldsAcrossStylesets` table to stay green (both NAV and LOCKED glyphs, several widths).
- **`x/vt` caveat:** its `Read`/`Close`/`Write` share an unsynchronised `closed` flag. Never call `emu.Read` from a second goroutine — that's why terminal-query responses are *not* forwarded to children yet. Keep all emulator calls on the bubbletea goroutine.
- **The `input`/`list`/`form` widgets embed a bubbles/huh component directly, not `scrollBox`** — deliberately, since `textinput.Model`/`list.Model`/`*huh.Form` already own their own scrolling, editing and (for `list`) filtering, so `scrollBox` would only be redundant plumbing. Three gotchas specific to hosting a third-party bubbletea component this way, inside *our* bubbletea program rather than as the whole program:
  - **No `tea.WindowSizeMsg` ever reaches a widget.** `engine.Model.Update` consumes it at the very top to size the layout tree and returns immediately — it is never part of the `default:` broadcast to leaves (see `internal/engine/engine.go`). `list.Model.SetSize` and `huh.Form.WithWidth/WithHeight` are called every `View(width, height)` instead (mirroring how `renderLeaf` already re-reads `Size`/`Direction` every frame elsewhere in this codebase) — `textinput.Model.Width` similarly gets set in `inputWidget.View`, not in response to a size message that will never come.
  - **`bubbles/list`'s default keymap binds `q`/`ctrl+c` straight to `tea.Quit`.** Left enabled, a keypress *inside one pane* would kill the whole multi-pane program — call `list.Model.DisableQuitKeybindings()` at construction (done in `newList`) and never remove it without replacing it with some other interception.
  - **Cursor blink (and any other self-re-arming animation cmd) needs every message forwarded, not just Key/Mouse.** `textinput`'s blink is kicked off by `Init()` returning `textinput.Blink` and then keeps re-arming itself via a message type only `textinput.Update` recognizes; `huh.Form` does the same internally for its own fields. `inputWidget.Update`/`listWidget.Update` forward every `tea.Msg` unconditionally (not just `KeyMsg`/`MouseMsg` the way `text`/`command` do) so that loop keeps ticking — engine.go's `default:` case is what delivers those blink messages here, broadcasting to every leaf same as any other unrecognized message type. Writing a test against one of these three widgets and draining every returned `tea.Cmd` naively means draining that infinite blink chain too, and each hop is a real `tea.Tick` (a real sleep, not simulated) — bound any such drain to a handful of steps (see `drainForm` in `internal/widget/form_test.go`) or a "just wait for the state to settle" test takes tens of seconds for no reason.

When you create auxiliary tooling `DESIGN.md` asks for (setup scripts etc.), keep the `Makefile` the single source of dev commands and update the block above.

## What this project is

A config-driven TUI/CLI framework in **Go**. A "TUI" is authored entirely as a config file (markdown/JSON, human-readable, splittable across files or consolidated into one file with sub-config sections). The framework turns that config into a running interface.

Three architectural pillars from `DESIGN.md`:

1. **Config-driven** — every TUI *is* its config: layout, behavior, keybindings, embedded scripts. No recompilation to change a TUI.
2. **Runtime and compiled execution** — a TUI runs by pointing the engine at a config path, *or* it compiles to an executable. Compilation has two linking modes:
   - *dynamic* — core engine + config kept separate
   - *static* — engine baked together with a specific config plus the modules/dependencies that config requires
3. **Multiplexing** — split, resize, position and manage screen space like a pre-configured tmux; run interactive shell commands and long-lived processes inside panes.

Cross-cutting requirements: full keyboard + mouse interactivity; unicode/ascii/ansi and Nerd Font support; first-class shell (zsh) scripting and integration, with python/node as secondary; animations and localized non-static rendering; and **total modularity** — anything that could reasonably be modular, swappable or config-driven should be.

All of this lives behind the widget layer, not the engine — the rule that added them ("a `form`/`input`/`list` widget would be the first to pull `huh` in — widget file, not engine") is the same rule that governs adding the next one.

## Working constraints

- **Runs on a live production Arch Linux system with no sandbox.** Be careful with destructive operations.
- **Use git.** Work on a branch; never commit straight to `main` or merge without asking.
- **Minimalism over frameworks.** Build exactly what's required with zero overhead. Don't pull a heavy dependency for one small task — write the snippet or cherry-pick it. Continuously question whether a solution is over-complex.
- **Design authority.** Follow `DESIGN.md`'s intent closely *where it makes sense*. If an instruction is impossible, wrong, or wasteful, do it the better way while still delivering at least what was asked. If something clearly should exist, build it even if unmentioned. (`DESIGN.md` is now vision + design requirements only — the agent/software-design rules it used to carry live in this section now.)
- **Clarify only high-stakes unknowns.** For low-stakes ambiguity, make a best-effort call and proceed.

## Token discipline

The global golden rules (see **Rule precedence**) are always in force here — the "free savings" (batch calls, grep before read, don't re-read after edits, stop when you know, cheap model for mechanical work) are not optional.

An optional stricter "eco mode" tightens the ratchet further: pinpoint context with `rg`/`fd`/`sed` before reading; never `cat` a >250-line file just for context; keep reasoning effort low unless the task genuinely needs more; terminal-style output with zero filler; take an explicit `[Bypass: requires deep context]` escape hatch rather than looping on retries. If eco mode and the global rules ever disagree, the global rule "never cut reasoning quality to save tokens" wins.
